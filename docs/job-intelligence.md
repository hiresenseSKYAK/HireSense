# Job intelligence implementation and operating notes

## Candidate context and ranking

The authenticated `POST /ai/jobs/recommendations` accepts the same bounded resume DTO as existing career coaching. The server removes contact data and keeps at most 30 skills, six titled experience/project entries with two short evidence bullets each, three education items, and three repeated coaching signals from the requesting user's completed interviews. It does not create a free-form memory or persist a candidate profile. Cached responses use a per-user SHA-256 fingerprint of this context and the selected live job snapshot; the in-process cache has a 256-entry bound and is not shared across workers.

The live catalog is still authoritative. Existing entry-level/geography filters, active-row policy, URL identity upsert, conservative cross-source deduplication, and link closure checks run before personalization. Deterministic ranking uses resume/posted-skill overlap, title relevance, source posting age where known, early-career level, and presence of a direct apply link. Jobs with no demonstrated skill overlap do not enter the compact recommendations. `Strong fit`, `Worth exploring`, and `Stretch role` describe search priority, not hiring probability. A visible reason names a real overlapping skill and, where present, a literal resume bullet. A missing skill is drawn from posting data. Repeated interview weaknesses add only a preparation note; they never lower the match score.

When the light model and per-user budget are available, one structured call returns an ID order for at most 12 deterministically shortlisted jobs. The server accepts it only if every ID appears exactly once, and only reorders within ten-point deterministic score bands. Provider failure, invalid order, or budget exhaustion leaves the deterministic order. This is semantic tie-breaking, not free-form LLM ranking. The original paged feed and all selected filters remain deterministic. Its natural-language query parsing only expands terms over existing title/company/location/tags/short description; it does not bypass structured city, work-style, seniority, salary, type, date, or skill filters.

The homepage shows up to four recommendations when a signed-in user chooses **Use my resume**. This opt-in also controls skill matching in the normal feed. Locally saved resumes are bound to the uploading account; an older unbound/guest resume is bound to the first signed-in account that uses it, then hidden from other accounts on the same browser. `New since your last visit` counts recommendation IDs absent from this browser's previous per-user recommendation snapshot. It is not a posting-age or active-status claim. Job detail already has authenticated on-demand preparation; the panel now leads with priority, supported resume evidence, top gaps, application emphasis, and likely interview areas.

## Sources and freshness

The scheduled GitHub Action runs every six hours against bounded LinkedIn and Handshake public discovery plus configured direct Greenhouse, Lever, and Ashby employer feeds. Each source can fail without suppressing the others. Direct ATS sources provide structured employer postings but cover only configured boards. No new scraping or credentials were added in this pass. `datePosted` is shown only when supplied; `firstSeenAt` is discovery time and never presented as a source posting date. Older-than-90-day source dates are deprioritized, not silently deleted. Existing link checks deactivate only confirmed 404/410 or explicit closed pages; inconclusive responses remain visible, so availability is never guaranteed.

Source limitations remain: LinkedIn/Handshake public pages can change layout or rate-limit; some dates and requirements are absent or imprecise; configured ATS boards cover a small employer set; six-hour scheduling does not guarantee jobs were posted in the last six hours; and link checks are weekly only for old/undated rows. Operators should review per-source crawl health and stale/duplicate counts after each run. Do not expand sources with prohibited or brittle scraping.

## Models, cost and validation

`OPENAI_INTERVIEW_MODEL` → `OPENAI_MODEL` → `gpt-4o-mini` routes interview operations. `OPENAI_LIGHT_MODEL` → `OPENAI_MODEL` → `gpt-4o-mini` routes resume coach, job preparation, and bounded recommendation reranking. `OPENAI_API_KEY` is required for model calls; no new service or credential is required. `OPENAI_TIMEOUT_SECONDS`, `OPENAI_MAX_OUTPUT_TOKENS`, and `OPENAI_MAX_RETRIES` remain bounded. Career requests share the existing in-process 20-call/user/hour budget; identical cached requests do not consume it. Interview repair can add at most one provider call per eligible evaluation and counts toward session/user provider limits.

No numerical price or model winner should be asserted without measured tokens and a live benchmark. For each operation, estimated standard token cost is `(input_tokens × current_input_rate + output_tokens × current_output_rate) / 1,000,000`; multiply the measured per-call amount by seven baseline calls for a five-question interview (generation + five evaluations + debrief), plus the observed rare repair count. A job-prep or resume-coach request is one light-model call on a cache miss. A 20-job feed makes **at most one** light-model rerank call, and only if at least three qualified shortlisted jobs remain. Use the provider's logged token counts and the current model price table; do not treat these as fixed dollar quotes.

`python -m scripts.benchmark_models` compares synthetic technical and behavioral evaluations, job fit, resume critique, and job reranking across the baseline and distinct configured models, reporting schema validity, conservative grounding checks, latency, and tokens without printing content. It requires an intentionally configured API key and incurs charges. Review outputs manually for specificity and truthfulness before changing the production model. The deterministic fallbacks and current `gpt-4o-mini` default remain until evidence supports a different choice.

## Production verification

1. Set backend-only `OPENAI_API_KEY`, `OPENAI_MODEL`, optional interview/light overrides, timeout/output/retry variables, and existing database/CORS settings in Render.
2. Run database migrations, confirm the six-hour crawl and each source's status, and compare active unique row counts with `GET /jobs/`.
3. Sign in with a test account, upload a synthetic resume, enable **Use my resume**, and verify top reasons quote only that resume and listed skills; disable it and confirm original filters/order.
4. Confirm a missing posting date shows no `Posted today` label, an old listing ranks lower, and a confirmed closed link disappears after the checker.
5. Complete two owned practice turns with the same explicit skill gap; verify a preparation note appears only on related roles and match score does not change. Repeat with a second account to check isolation.
6. Open job preparation and verify every requirement, resume quote, gap, and application suggestion against the source posting and resume. Confirm no claim of hiring odds, active availability, or submitted application.
7. Inspect sanitized `career_ai` and `interview_provider` logs for accepted/repair/fallback counts, latency, and token usage; verify no raw resume, answer, key, or model output appears.
8. Run the opt-in model benchmark with real configured candidate models, review quality manually, calculate costs from measured usage, and only then choose production overrides.
